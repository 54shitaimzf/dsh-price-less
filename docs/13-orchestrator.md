# 13 · 编排域：task 内可并行子目标的上下文压缩执行

> 域定义：**编排域执行"一个 task 中可并行子目标集合"的方法**——用公共前缀共享 + 增量机械，
> 把该子目标集合以更低上下文包袱跑完。管道是 task 内的一次性调用（调用-执行-返回），
> task 生命周期由输入域（docs/03）管理。
> 默认关：门控判定适用才开启，否则串行（+文件治理）即基线。

## 0. 它解决什么问题（人话版）

这章讲"把一个 task 里能并行的子目标凑在一起，用一次调用跑完"的办法，**默认关**。痛点是：一个任务里常有 3、4 个互不依赖的子目标，各自拿去开子代理，每个子代理都把当前上下文**整份拷给**自己的会话（N 份全量），又贵又慢。思路是**管道（编排域）**——把一个任务里的并行子目标聚合成一次调用：指挥 agent 负责拆分，执行 agent ×N 各干一小片，汇总 agent 把结果收回来；关键是让所有执行段**共享同一个 P**（一份对象，缓存复用），每段只加一点点增量，而不是各拷一份文本。收益是缓存全命中（×N 复用）、省墙钟时间（并行跑），且总模型调用数不变；代价是**只有拆得开才划算**——所以要先做"L0 可分性门控"，拆不开就老老实实回退串行。默认关：只有当门控判定"能拆"才启用，否则串行（+文件治理）才是基线。

## 1. 位置与生命周期

```
task（输入域维护的唯一状态机）
 ├─ 子目标 A(串行) → 主会话直接做
 ├─ 子目标 B/C/D(可并行) → 【管道】调用 → 执行 → 修改流汇回主会话
 └─ 子目标 E(串行) → 主会话继续
```

- 管道输入：`goal`（锚定产物，提示词域）+ `scope`（文件集——优先取意图映射坐标 docs/15，未命中取工具引用统计）+ P（主插件）;
- 管道输出：修改流（结构化补丁）+ 汇总叙述;
- 执行完即返回主流程，无持续状态（中间态仅在日志追账）。

管道是 **task 内的一次性调用**：调用 → 执行 → 返回，不产 task 边界、也不消费 task 边界，task 生命周期归输入域（03）。管道输入里，`scope` 明确的文件集**优先取意图映射坐标**（docs/15 给出文件/符号/行号），没命中就退一步用工具引用的统计；输出是一份**修改流**（结构化补丁清单：文件+行区间+替换文本+版本戳，机器能应用能验证）加上一段汇总叙述。中间态不落地，只在日志里追账。

## 2. 公共前缀复用

```
指挥 agent : P + 任务拆分
执行 agent ×N: P + 拼接拆分任务 i    ← 短会话(3–5轮)无状态
汇总 agent : P + 修改流汇总 + 叙述
```

- P 目标内恒定 → 各段请求缓存全命中；与"把上下文拷进 prompt 的传统子代理"的区别 = **对象共享**(§6);
- 每段增量极小; 执行段并行共享同一 P（缓存复用 ×N，省墙钟；总模型调用数不变）。

这就是**对象共享 vs 文本拷贝**的核心差异：传统子代理把上下文**拷**给每份子会话（N 份全量文本进 prompt）；本域让所有执行段**共享同一个 P**（一份对象，附着过去、不进历史），缓存复用 ×N。P 在目标内恒定，所以各段请求的**缓存前缀**（请求开头不变的部分）全部命中——变了就白算，不变就复用。省的是墙钟时间（并行跑），总模型调用数不变。

## 3. L0 可分性门控

**L0 可分性门控**就是"纯代码预检能不能拆"：看文件重叠度、依赖宽度、单元性，不达标就回退串行。判据全在这张表。

| 判据 | 计算 | 不达标 |
|---|---|---|
| 文件重叠度 | 子目标间共享文件/符号的加权重叠 | 高 → 强耦合 → 回退串行 |
| 依赖宽度 | 子目标依赖图平均扇出 | ≈1 → 无并行收益 → 回退串行 |
| 单元性 | 单文件单处修改 | 无拆分意义 → 回退串行 |

门控不通过 → 返回 `fallback`（管道工具给出明确回退,调用方走串行）。

三个判据说白了：**共享文件/符号越多越别拆**（强耦合拆开会打架）、**依赖扇出接近 1 就别拆**（互相等着，没并行收益）、**本来就单文件单处修改就别拆**（没有拆分意义）。任一不达标就走 `fallback`，管道工具给出明确的回退，调用方老老实实串行。

## 4. 修改流契约

- 执行 agent 产物 = 结构化补丁（file + 行区间 + 替换文本 + 版本戳 vN）；
- 合流：补丁按序应用; 版本戳 CAS 冲突 → "归属失败"返回执行 agent 重取;
- 汇总两条通道：
  - 机械通道（L0）：补丁链 + 文件版本 + 变更清单 → 机器应用、可验证、逐字保真;
  - 叙述通道（L1/L2）：仅用于汇报 / L3 知识与下一目标提示——叙述与机械操作在输出中分离;
- 补丁可执行性由主插件补丁守卫裁决（docs/12 §4）。

**修改流**是执行 agent 交回来的结构化补丁：每个补丁带 file（哪个文件）、行区间、替换文本、以及**版本戳 vN**（第 N 版）。**合流**就是把这 N 个执行 agent 的补丁按序合并应用；**版本戳 CAS**（写前版本号校验，不一致就拒绝）一旦冲突，就判"归属失败"，把补丁退回去让那组执行 agent 重取。汇总走两条分离的通道：**机械通道（L0）**产出补丁链+文件版本+变更清单，机器应用、可验证、逐字保真；**叙述通道（L1/L2）**只用于汇报、喂 L3 知识与下一个目标的提示，不掺进机械操作。补丁到底能不能执行，由主插件的**补丁守卫**（docs/12 §4）裁决。

## 5. 采用层（三层,按确定性降序）

**采用层（L0/L1/L2）**是三层渐进的推广方式：每步预检提示 → 模板嵌入管道意向 → 用户显式命令。强度从软到强，看这张表。

| 层 | 触发 | 强度 |
|---|---|---|
| L0 挂点预检 | `agent/pre-step` 对当前 task 做可分性预检 → 通过则追加一行引导 | 软提示但每目标必现 |
| L1 模板嵌入 | 提示词域"管道任务模板"命中 → 锚定段含管道意向（用户可审） | 最强（用户背书） |
| 命令 | `/run-task-pipeline` 用户显式触发 | 显式 |

引导强度为**静态配置**（`pipelineEmbed` 0–3,默认 0）;invoke/fallback/success 三率（docs/07）供实验判定与人工调参（docs/08）,运行时不自适应。

大白话：**L0 层**在 `agent/pre-step` 对当前 task 做可分性预检，通过就在引导里追加一行，软提示但每目标必现；**L1 层**是提示词域的"管道任务模板"命中，锚定段里就带上"这活儿走管道"的意向，用户可得见、可审，是最强的一档（用户背书）；**L2 层**是用户用 `/run-task-pipeline` 显式触发。引导强度（`pipelineEmbed` 0–3，默认 0）是**静态配置**，运行时不会自己调参——invoke/fallback/success 三率（docs/07）留给实验判定与人工调参（docs/08）。

## 6. 与传统子代理的差异

| | 传统子代理 | 本域 |
|---|---|---|
| 上下文传递 | 文本拷贝（prompt 内联） | 对象共享（P 附着,不入历史） |
| 任务粒度 | 全量描述 | P + 小增量（片段 i） |
| 分工 | prompt 约定 | 架构固定（指挥/执行/汇总） |
| 返回物 | 自由文本 | 修改流（schema 补丁）+ 叙述 |

保留: 独立会话、扇出/归并、一次委派拿结果。

一句话概括这张对比表：传统子代理是"**拷文本**"——把全量描述内联进 prompt；本域是"**共享对象**"——P 附着过去、不入历史。传统子代理任务粒度是"全量描述"、分工靠 prompt 约定、返回自由文本；本域是"P + 小增量（片段 i）"、分工是架构固定（指挥/执行/汇总）、返回是修改流+叙述。两者都保留了独立会话、扇出/归并、一次委派拿结果这些优点。

## 7. 事件与度量

- 事件：`pipeline/split`、`dispatch`、`merge`、`fallback`、`complete`（log-only）;
- 度量：`pipelineInvokeRate`/`pipelineFallbackRate`/`pipelineSuccessRate`、`templateEmbedRate`、`parallelWidth`、`ownershipMissRate`、`handoffWaitTurns`。

这些事件都是 **log-only**（只记日志、可回放、不触发副作用），用于追账与重放。度量里 `parallelWidth` 是并行宽度、`ownershipMissRate` 是归属失败率（合流时的 CAS 冲突比例）、`handoffWaitTurns` 是交接等待轮数。

## 8. 验收标准

- [ ] 门控回退后行为与串行基线一致（配对断言,docs/08）;
- [ ] 补丁链 100% 机械可应用（schema 校验 + 合流测试）;
- [ ] 三段请求 P 前缀字节一致（回放断言）;
- [ ] 关闭本域后其余域功能完整。
