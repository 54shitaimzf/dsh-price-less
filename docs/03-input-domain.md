# 03 · 输入域：task 生命周期发现

> 域定义：**输入域发现 task 的生命周期**——确认一个 task 的结束与下一个 task 的开始，并随边界产出 task 定义。
> 判定口径：**机械信号为主 + 少量 embedding 加权**。本域是纯发现器：知识沉淀在主插件（docs/12），
> 知识应用（锚定）在提示词产品域（docs/04），体积执行在压缩域（docs/02）。
> **task 单一明确**：task 定义 = `{ taskId, 边界, 证据 }`（边界单元，不含意图语义）；意图的唯一来源是文件与寻址域（docs/15）。
> 本域负责观测"意图漂移信号"用于判界；意图的定义、存储与检索由文件与寻址域（docs/15）负责。

## 0. 它解决什么问题（人话版）

一个会话里，agent 可能一口气干好几件事：先改一个 bug，再补一个测试，最后又去重构另一个模块。每一件事就是一个"task"。难点在于**agent 不说"我这件干完了、开始下一件"**——你只能从它用的工具、打的字、停留的时间里"猜"出边界在哪；而猜错边界，后面压缩、锚定、归档全跟着错位。输入域（03）就是那个**负责判边界的观察员**：它被动地看信号，确认一个 task 的结束和下一个 task 的开始，并在边界时产出一份 task 定义。

它的思路是**机械信号为主 + 少量 embedding 加权**：能靠规则算出来的（用户显式命令、文件读写的重复、todo 完成度、静默时长）绝不麻烦模型；只有这些机械信号不够时，才用一点向量相似度搭把手。因为判界本质是**意图漂移检测**——用户的意图变了，task 就切了。

task 是"这一单活"，定义为**边界单元**：`{ taskId, 边界, 证据 }`。它的职责是记录**这单从哪条消息开始、到哪条消息结束、凭什么判的边界**；"这单在改什么功能"属于意图，由文件与寻址域（docs/15）定义与持有——意图只有一个地方能定义，谁都不许自己另搞一套。

收益是量化的：边界判得准，`roundsPerTask` 才合理，压缩和锚定都踩在对的时机上，task 表能从日志回放重建。代价是边界总要"等证据"——所以我们宁可**晚切**（fail-lazy：证据不足就维持当下，宁可晚切不可乱切），也不要在证据不足时急吼吼切一刀造成错位。这些信号大多数用机械方式就能判定；只有在 `embeddingTier:'off'`（向量档关着）时，语义票才退化成关键词 + 路径前缀的机械等价物，照样能判。

## 1. 什么是 task（本域的口径）

一个 task = 用户工作意图在语义上的一个稳定单元（**执行单元**，非知识单元）。task 定义（不含意图语义）：

```
task = { taskId, 边界: { start, end }, 证据: signals[] }
```

以 task 为单位管理执行：语义意图变化 = task 边界（判界信号）。发现 = **意图漂移检测**；
意图的定义、结构、检索、归档由文件与寻址域（docs/15）负责；本域只观测漂移信号作为判界依据。

> 打个比方：task 是"这一单活"，`{ taskId, 边界, 证据 }` 就是它的"工单"。工单只记录**这单从哪条消息开始、到哪条消息结束、凭什么判的边界**；"这单在改什么功能"属于意图，由文件与寻址域（docs/15）定义与持有——意图只有一个地方能定义，谁都不许自己另搞一套。

## 2. 判定信号（加权，机械优先）

| 信号层 | 内容 | 权重 | 来源 |
|---|---|---|---|
| T0 权威信号 | 用户显式 `/task`、`/task close`、`plan/mode`、`goal/change`、`todo/write` | 一票（任一命中即边界） | 命令/事件 |
| T1 机械签名 | 工具 Jaccard 相似度（同文件重复读写 = 意图连续；跨文件切换 = 边界候选）、`todoCompletedRatio` 达成、静默时长 ≤ `taskSilenceMs`、修复识别（patch write overlap，延续旧 task） | 主 | `tool/call`+`tool/result` |
| T1 lexical | 用户纠正/否决（"不要X/改用Y"）、目标/风格关键词、新指令意图词 | 主 | `user/message` |
| T2 语义票 | 本地 embedding 意图相似度（`taskEmbeddingThreshold`），作为 T1 的第 2 票（不单独触发） | 辅 | L1 embedding（'off' 时机械降级为关键词+Jaccard） |

> 这张表的信号分层：**T0（一级）**是用户显式命令，一票算数——用户说"换任务"就是换，最大；**T1（二级）**是机械签名——同一文件反复读写、清单完成度、静默太久、又在修同一个旧文件，这些靠规则就能算；**T2（三级）**是向量相似度，只做辅助，从不单独决定。权重列里的"一票/主/辅"就是在说：T0 命中了直接算边界，T1 是主力，T2 只能当第二票。

**组合规则**：
- T0 命中 → 边界成立（显式 > 一切）；
- 无 T0 → T1 需 2-of-3 合议（结构签名 / lexical / 语义票）；
- fail-lazy：证据不足时维持当前 task（宁可晚切，不可乱切）。

> **2-of-3 合议**：三个机械信号（结构签名、lexical、语义票）里，至少两个同时成立才判边界。这是怕单个信号误判——比如一次普通的文件切换就被当成任务切换。**fail-lazy**：证据不够时，宁可先维持着当前 task 不切，也绝不乱切一刀造成错位。

## 3. 产出

```
task-boundary {taskId, kind: 'explicit'|'signals'|'explicit-close', signals[]}
task-binding   {sourceTaskId, kind, signals[]}      ← 检测到"当前工作延续旧 task"(修补/继续)
task 定义 = { taskId, 边界, 证据 }（无意图字段——意图查询走 docs/15）
             → 主插件(归档) + 压缩域(体积) + 提示词域(锚定重建时机) + 编排域(管道入口)
```

> 本域的职责是**发事件**：判出边界时发出 `task-boundary`（检测到"还在延续旧任务"时发 `task-binding`），并产出 task 定义 `{ taskId, 边界, 证据 }`——意图字段不存在，想知道"这个任务在干嘛"去 docs/15 查。

## 4. 边界确认后的分工（本域只发事件）

| 消费方 | 拿边界做什么 |
|---|---|
| 主插件 | task 结束 → L3 差分 + 意图映射表更新 + 工作摘要归档 |
| 压缩域 | task 结束 → 体积归档（旧 task → 摘要区） |
| 提示词产品域 | 新 task → 锚定重建时机（意图内容自 docs/15 读取，不经本域） |
| 编排域 | 新 task 定义 → 可并行预检（管道是否适用） |

> 判出边界后，后续动作各有归属：主插件沉淀知识、压缩域归档体积、提示词域重建锚定、编排域评估并行——它们都消费本域发出的边界事件与 task 定义。

## 5. 事件与度量

- 事件：`task-boundary`、`task-binding`（log-only，回放 **fold 重建** task 表——按事件顺序重放日志重建任务表）；
- 度量：`roundsPerTask`（边界切分口径）、`taskSwitchRate`（漂移检测触发率）、`taskDefinitionBytes`（task 定义字节）。

## 6. 验收标准

- [ ] T0 显式边界在任意状态下优先成立；
- [ ] 重复文件读写签名可复现（同一文件反复读写不触发边界；切换文件触发候选）；
- [ ] `embeddingTier:'off'` 时语义票显式缺位、T1 按 2-of-2 合议（判定仍可用）；
- [ ] task 表可从日志事件 fold 重建（重启后一致）；
- [ ] task 定义无意图字段（意图唯一来源 = docs/15）。
