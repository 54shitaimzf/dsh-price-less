# 09 · L3 状态存储模型

> L3 是系统的**单一事实源**：主插件（自动差分写）、提示词产品域（用户编辑写）、
> 提示词产品域（锚定读）、文件与寻址域（映射表复用本协议）。
> 版本号是贯穿全部件的货币；一致性靠"成对提交"，锚定层与映射层共享同一版本源。
> 工作摘要**按 task 归档**（任务级知识单元，非意图定义——意图唯一来源在 docs/15），偏好/映射为跨 task 沉淀。

## 0. 它解决什么问题（人话版）

模型跑完一个任务，学到的东西（偏好、代码在哪、要注意什么）如果不存下来，下回又得从头摸索；更糟的是，如果存的地方不唯一、或者被两处同时改，就会互相打架、版本错乱。所以这套件把模型沉淀下来的知识做成一块 **L3 知识存储**，当成系统的**单一事实源**（唯一权威版本）：主插件在 task 结束时自动**差分写**（只记录变化的部分：新增/变更/删除，没变的字节不动），提示词产品域在做用户编辑时也写回，两边共享同一套版本协议。这样设计的好处是：知识可复用、可回滚，且锚定段（提示词产物里钉住"为什么做、去哪改"的几段）能**字节稳定**（同版本内容逐字节一致——缓存能命中）。代价是：每次写入都要带版本和来源（source）来防冲突，落盘要**原子写+rename**（先写临时文件再改名覆盖，中途断电也不留半截文件）。核心一句话：**同一版本源永远不许漂移，改一处必须成对提交**（两处变动同一次落盘，要么都成、要么都放弃）。

## 1. 存储形态与位置

| 项 | 决定 |
|---|---|
| 位置 | `$DSH_HOME/.context-economy/knowledge.json` 单文件（+ 原子写临时文件再 rename）——映射表 `mappings` 实体内嵌其中（成对提交原子化，docs/12 §7–8）；拆为独立文件属于架构变更，须重新裁决 |
| 格式 | JSON（人类可审、可 diff、可回滚）；任务集规模小，JSON 单文件足够 |
| 扩到 SQLite 的时机 | 映射条目 > 5k 或并发写者 > 1 时再迁移（决策留痕） |

## 2. 实体与版本协议

```jsonc
{
  "schemaVersion": 1,
  "preferences": { "version": 7, "items": [
    { "id": "pf-3", "text": "…", "source": "task-12:user-correction", "updatedAt": "…" }
  ]},
  "taskSummaries": { "version": 9, "archived": {   // 按 task 归档的工作摘要（非意图定义——意图唯一在 docs/15）
    "task-12": { "summary": "…", "constraints": ["…"], "targets": ["src/index.ts"] }
  }},
  "mappings": { "version": 6, "items": [
    { "intentId": "task-12", "targets": [
      { "file": "…", "symbols": ["…"], "lineRange": [1, 40], "toolPath": "read", "confidence": 0.9, "evidence": "tool/call@task-12" }
    ]}
  ]}
}
```

这里每个实体都带自己的 `version`（版本号）和 `schemaVersion`（数据结构版本号）。几个关键约定：

- 各实体**独立版本号**（单实体差分，不整库升版）；
- 版本号单调递增；每次写入必须可回放（记录 `source` 溯源：哪个 task/事件的证据）；
- **差分能力**：写入只携带增量（新增/变更/删除条目），不变条目字节不动 → 锚定段同版本字节稳定；
- 工作摘要按 task 归档（task 定义不含意图——活 task 只绑定意图节点，意图定义/版本唯一在 docs/15；L3 存放完成归档的摘要与偏好/映射）。

## 3. 读写者矩阵

| 角色 | 动作 | 触发 |
|---|---|---|
| 主插件 | 写（差分，版本+1） | task 结束证据 → L3 差分 + 意图映射表同事务（docs/12 §7–8） |
| 提示词产品域 | 读（锚定指针）+ 写（用户编辑 → 高信号纠正） | 优化提示词 / 预览编辑确认 |
| 输入域 | 读（task 边界/证据——意图不经本域，检索走 docs/15） | 发现判定时 |
| 文件与寻址域 | 映射表读写（复用本协议） | task 周期更新 / 检索 |
| 度量账本 | 只读（审计快照） | 连续 |

## 4. 写入规则

写入不是想写就写，四条规矩定死：

1. 差分必须附带 `source`（任务 ID + 事件类型 + 证据），无来源的写入拒绝；
2. 同实体同轮只允许一次提交（锁在进程内互斥，防主插件/提示词产品域并发写）；
3. 每次提交先 `schemaVersion` 校验，再 `version+1` 原子落盘；
4. 用户编辑（提示词产品域）优先级高于自动差分（主插件）：同轮冲突时用户编辑胜，自动差分推迟到下一 task。

## 5. 一致性闭环（锚定层与映射层共享版本源）

```
用户编辑（可见层,提示词产品域） → 差异 → 差分写 L3 + 意图映射表更新 → 版本+1
        │                                              │
        └── 下一轮锚定（提示词产品域）按新版本渲染 ──────┘
```

任何一处版本不一致必须触发告警事件（`context-economy/version-mismatch`）。

## 6. 回滚与审计

- 每次提交保存 `knowledge.json.<version>` 快照（保留最近 N=50 版）；
- 回滚 = 重建快照 + 版本指针回退；回滚同样记 `source: rollback@<version>`；
- 审计：`/context-economy/api/history` 返回全部提交（version/source/Δ 条数）。

## 7. 验收标准

- [ ] 无来源写入被拒（单测）；
- [ ] 同版本锚定段逐字节一致（哈希 CI）；
- [ ] 并发写（主插件 vs 提示词产品域）不丢版本（互斥 + 原子写）；
- [ ] 工作摘要按 task 唯一（同 task 二次归档拒绝/合并）。
