# 06 · 缓存前缀纪律（字节稳定）

> 前缀缓存是本套件最大的免费午餐。三条铁律（含断言）如下——
> 违反任何一条,会让 [docs/01](01-architecture.md) 的 P 段、[docs/04](04-prompt-domain.md) 的模板与锚定、
> [docs/15](15-file-governance.md) 的文件流全部失去缓存价值。

## 0. 它解决什么问题（人话版）

**前缀缓存**是这套件里最大的免费午餐：请求开头那一大段如果每次一模一样，服务端就能直接复用算好的部分，不用重算——等于白拿的性能。痛点就在这：只要前缀稍微变一个字节（哪怕只是顺序变了、多插了一个空格），后面依赖前缀命中的计算**全白算**，钱照付。而且模型注意力有"中间易忘"特性（**lost-in-the-middle**），尾巴每轮都被重算，最贵。

思路是三条铁律，把前缀死死钉住：**同输入 → 同输出**（相同组装结果必须逐字节一致）；**稳定在前、动态在后**（稳定的放头区当缓存前缀，会变的放尾区）；**变更走 delta/版本**（要改就升版本号，一次目标级重建，绝不原地改写历史段）。

收益是量化的：只要守住这三条，P 段、模板主体、锚定段、文件流 vN、压缩摘要段全部可持续命中，前缀越长越划算。代价是纪律非常严格——内容一变只能升版本，不许原地改；热度另看冷/热两列报告（**冷缓存** = 清缓存后首跑，**热缓存** = 连续跑的命中率）。

## 1. 铁律

1. **同输入 → 同输出**：相同组装结果必须字节一致（模板主体、锚定段、P 段、文件流 vN、压缩摘要）。
2. **稳定在前，动态在后**：system、tools、P 段、模板主体 = 前缀；实例参数、用户指令 = 后缀。（前缀 = 请求开头不变的部分，变了后面全白算；后缀 = 允许每轮变化的尾巴）
3. **变更走 delta/版本**：内容变化 → 版本 +1 → 一次目标级重建；杜绝原地改写历史段。（**vN** = 第 N 版；改内容就升版本号，用版本号做写入前校验，不一致就拒绝——这就是**字节稳定**：同一版本内容永远逐字节一致）

## 2. 请求布局与命中覆盖

```
[system] [tools] [P 段: 文件流 vN + 压缩段 + 目标/步骤] [模板主体] [锚定段] [实例+用户指令]
   ←────────────────────── 稳定前缀（hit） ──────────────────────→ ←── 尾（重算）──→
```

- P 段：主插件组装（docs/12 §6），目标级更新——task 边界/管道模式切换时一次性重建；
- 锚定段：提示词产物内（docs/04 §2.1），同 task 同版本同字节——随产物进入历史，是稳定前缀的一部分；
- 模板主体：同类任务共享，字节稳定。

## 3. 位置纪律（与注意力/lost-in-the-middle 对齐）

- 用户指令恒为最后一条（最高近因）；锚定段位于产物内、指令之前；
- P 段前置于头区：越长越稳，避免尾巴每轮被重算；
- 尾部允许变化（实例参数/新消息），变化幅度 = 每轮重算成本。

## 4. 摘要与辅助调用前缀对齐

- 压缩摘要（压缩域）与任何辅助调用：复用会话自己的 system + tools + 消息前缀，
  指令作为最后一条 user 消息追加——辅助调用 = "上一次路由请求的真前缀 + 新颖尾"，缓存被复用而非失效；
- P 段在辅助调用中保持同版本（与主请求一致）。

## 5. 锚定段与文件流版本化

- 锚定段版本 = L3/意图映射表版本：同版本逐字节一致；版本升 → 提示词产物重建（可见层）与 P 段更新（隐藏层）成对提交；（**成对提交** = 两处变动同一次落盘，要么都成、要么都放弃——版本一致，绝不一面新一面旧）
- 文件流 vN 变更 → P 段文件流段更新（目标级），同事务更新锚定段引用。

## 6. 冷热分离度量

- 缓存命中率按冷/热两列报告（docs/07 `cacheHitInputTokens` 差分）；（**冷/热** = 清缓存后首跑 vs 连续跑）
- 前缀断裂事件（P 段更新、锚定升版、文件流切版）计入 `prefixRebuildCount`（docs/07）。

## 7. 验收断言

- [ ] 同版本锚定段逐字节一致（CI 每日断言）；
- [ ] 同版本 P 段逐字节一致（CI 每日断言）；
- [ ] 辅助调用前缀 = 上一次请求前缀（回放断言）；
- [ ] 模板主体在同类请求间字节一致。
